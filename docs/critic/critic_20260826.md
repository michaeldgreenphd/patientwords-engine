## MEDIUM-1 — every published `model_stats.json` records an unresolvable `+dirty` engine sha

`data/model_stats.json:_provenance.engine_sha` reads `cad6785b96e6+dirty` today,
`66ab0fa6a1cc+dirty` yesterday, and `+dirty` on **every** revision checked back through
2026-08-25. The site's headline cross-model statistics therefore cannot be reproduced
from any named commit: the recorded sha names a tree that never existed in history.

It is structural, not sloppiness. `paired_stats_rigor.py` runs mid-chain, after the
exporters have written `urgency_shift.json` and the j-lens payloads into the working
tree and before the cycle commits them, so the tree is dirty by construction at exactly
the moment the stamp is taken. Nothing is wrong with the numbers — the inputs are the
files on disk, which are the files that get committed seconds later — but the provenance
field, whose only purpose is reproducibility, currently carries no reproducible
information.

Two candidate fixes, owner's call (recorded as `decisions_pending`):
(a) stamp the sha of the commit the cycle is *about to* create — not available at run
time, so this means re-stamping after commit, which reopens the byte-stability property;
(b) cheaper and honest: record `engine_sha` as the clean parent sha plus an explicit
`dirty_paths` list of the chain outputs not yet committed. A reader can then reconstruct
the tree exactly. Recommend (b).

## LOW-1 — `--stamps` is documented to accept two spellings and accepts only one

`scripts/export_frontend_simulated.py:110-116`. The comment above `STEERED` says
"Accept either spelling (bare stamp or `pairs_<stamp>` stem) and normalise to the bare
stamp: `--stamps` takes bare stamps, but a payload's `batch` field carries the stem, so
both readings reach this flag in practice." The normalisation on line 116 is applied to
`--steered-stamps` only; `STAMPS` on line 110 is never normalised.

Hit live this cycle: the natural way to build the stamp list is to read `scenario['batch']`
out of the committed payload — which is exactly the stem spelling the comment says is
accepted — and the exporter died with
`FileNotFoundError: data/simulated/pairs_pairs_20260706T201750Z.json`.

Severity LOW **only** because it fails loudly and immediately; it cannot corrupt a
payload. But the comment actively invites the failing spelling, and the crash happens
after the exporter has already been given a valid `--frontend`, so a less careful session
could read it as a missing-batch problem and start "restoring" archive files.
Fix is one line: `STAMPS = [s.strip().replace("pairs_", "", 1) for s in ...]`.

into the warning count, or they should be suppressed behind a flag. Surfaced in today's
