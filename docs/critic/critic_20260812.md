## HIGH-1 · The claim-grade staleness is wider than the open decision says, and one of its premises is wrong

**Known in part.** `MODEL-STATS-PUBLISH-POLICY-20260810` already has the core of this on
the owner's desk, and the 08-10 verdicts entry already records that the recomputed
medical-model numbers moved. This finding is what that entry does not cover, plus a
correction to it.

`data/model_stats.json` and `data/convergence.json` on the site are both stamped
`generated_utc` **2026-08-08T13:5x**; `data/timeline.json` is stamped
**2026-07-14T13:42:38Z** (29 days). The site's `CLAUDE.md:56-64` states all three are
"regenerated by the engine's nightly cycle." They are not. `paired_stats_rigor.py`
appears nowhere in the ops chain — not in `docs/routine_standing_prompt.md` §5, not in
the `publish-site-data` skill. Its only mentions in either file are the holdout
prohibitions ("never run paired_stats on holdout rows"). The generator is therefore
run only by hand, and has not been run since 08-08 while its inputs grew every cycle.

**The gap is not cosmetic — it inverts a published verdict.** The site's cross-model
comparison (`technical/` Part 4) still reads:

| model | published (08-08) | dashboard recompute (08-10, probe only) |
|---|---|---|
| meditron3-8b | n=132, CI95 [-0.0498, **+0.0004**] — straddles zero | n=333, CI95 [-0.0493, **-0.0211**] — excludes zero; sign test 23v3, q=1.76e-04 |
| apertus-8b-meditronfo | n=104, CI95 [-0.0657, -0.0032] | n=305, CI95 [-0.0464, -0.0127]; sign test 11v4, q=0.118 |

So the published payload **understates** what the data now supports for meditron3-8b,
and the `MEDICAL-FINETUNE-FRAMING-20260808` decision the owner is being asked to settle
is being judged against numbers the study has already superseded. The 08-08 dashboard
note anticipated exactly this hazard ("the hazard is a session writing 'the medical
models show it too' off the CI alone") — the mirror-image hazard also now exists: the
site's own numbers are the stale ones.

**What is new, beyond the open decision.**

1. **It is not one file.** The decision names `model_stats.json`. `convergence.json` is
   equally stale (08-08), and `timeline.json` has been frozen since **2026-07-14** — 29
   days — with no `engine_sha` at all.
2. **A premise in the 08-10 entry is wrong.** It says model_stats "is the only major
   payload with no `generated_utc`, so no automated check can see the staleness." Both
   `model_stats.json` and `convergence.json` carry `_provenance.generated_utc` — that is
   how the dates above were read. The proposed staleness check therefore needs no
   stamping work first; it can be written today.
3. **The doc is wrong, not silent.** Site `CLAUDE.md:56-64` positively asserts all three
   are "regenerated by the engine's nightly cycle." A session reading it would reasonably
   assume freshness rather than go looking.

**Not fixed here, deliberately.** Regenerating claim-grade stats mid-backfill would
move published numbers underneath a framing sentence the owner has an open decision on,
which is precisely what the 2026-07-15 framing gate forbids — the same reason the 08-10
cycle declined. Recorded as an update on the existing decision rather than as a new one.

## MED-3 · The circuit-trace lane is being starved by Neuronpedia rate limiting

**5 of the last 7 circuit-trace runs failed**, all on the same cause — HTTP 429 from
`https://www.neuronpedia.org/api/graph/generate`, exhausting all four attempts
(15s/30s/60s backoff) and aborting the batch mid-run:

| run | started | outcome |
|---|---|---|
| 31541670027 | 08-11 22:16 | failure |
| 31551617521 | 08-12 00:50 | failure |
| 31560086215 | 08-12 03:26 | failure |
| 31568524267 | 08-12 06:02 | failure |
| 31579145275 | 08-12 08:37 | success |
| 31591408761 | 08-12 11:20 | failure — 20 of 22 pairs, died at pair 21 |

Per-pair checkpointing means each failure still commits partial output, so the data is
not lost — but each burns ~85 minutes of runner time, and the batch truncates wherever
the 429 lands. The trace axis is the study's binding constraint (`tierb.traced_pairs`
1,580 of 1,600 on hosted graphs), so this is the lane where starvation costs most.
The retry ladder tops out at 60s, which is short against a sustained quota block.

Worth the owner's attention because the fix is a policy choice, not a bug fix: lengthen
the backoff ladder, cut trace chunk sizes, or space the accelerator's fires (all three
lanes currently fire within ~20 seconds of each other, e.g. 11:20:17 / :32 / :35).

## Feed-forward — the check that would have caught HIGH-1 and HIGH-2

Neither finding is subtle; both survived because nothing asserts them. Proposed, for
`validate_frontend_contract.py` (cheap, offline, no new inputs):

1. **Freshness assertion.** For each payload carrying `_provenance.generated_utc`,
   error when the stamp is older than a per-file budget (suggest: 48h for
   `model_stats.json` / `convergence.json`, which the docs claim are nightly; the
   others report-only). This turns "the docs say nightly" into something enforced.
2. **Dirty-provenance assertion.** Error on any `_provenance.engine_sha` ending in
   `+dirty` for claim-grade payloads. A number the study presents as claim-grade should
   not be traceable to an uncommitted tree.
3. **Chain-parity assertion.** Cross-check the writer names in the site `CLAUDE.md`
   data-contract table against the scripts the cycle actually runs, and flag any file
   whose documented writer is never invoked. That is the general form of HIGH-1, and it
   would also catch the next `timeline.json`.

Written as a proposal, not implemented: adding an erroring assertion to the gate that
guards publishing is an owner-visible policy change, and the first run would fail the
gate on three files that are stale today.
