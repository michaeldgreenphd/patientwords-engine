## HIGH · The lane sat completely idle for two days, and this is the third time

`ops/trigger_journal.jsonl` records **zero fires on 2026-08-01 and
2026-08-02**. All eight lanes were at 0 active when today's cycle opened;
`ops/dashboard.json:updated_utc` was 64h stale (watchdog threshold 26h). The
$0 lanes — hosted tracing, lens readouts, CPU logits — are the study's only
real throughput constraint, and they ran nothing for ~48h while Tier B sits at
1,200/1,600.

This is not a new hazard, it is the one already written down in
`docs/routine_standing_prompt.md` §4a: the daily cycle fires *into the main
orchestrator session*, and the "backfill accelerator" that was supposed to keep
lanes full **does not exist** (corrected 2026-07-27; never fired once in 280+
journal entries). The standing prompt already predicts the exact failure —
"assume the lane is driven ONLY by this daily cycle plus whatever in-session
timers happen to be alive… observed cost 12.7–21.6h per reclaim". Aug 1–2 is
that prediction landing at 48h.

What is new is the *evidence pattern*: three separate multi-day idles now
(07-24..27 at 54.7%, the 07-30 overnight gap, 08-01..02 at 100%). The 2026-07-10
mode change — Routine fires into the main session instead of a fresh one —
removed the redundancy layer §6b was designed around, and nothing replaced it.

**This needs an owner decision, not a code change** (recorded in
`decisions_pending`): either (a) approve the fresh-session Routine so a
container reclaim cannot silently stop ops, or (b) accept the throughput and
stop treating gaps as anomalies — in which case the pace language in the briefs
should say "runs when the session runs", not "daily".

I did not attempt to create any Routine: `create_trigger` requires an in-client
approval this session cannot satisfy (documented 2026-07-20 and 2026-07-26), and
inventing a workaround would repeat the false-accelerator error.
