## 5 · Feed forward — the check to write

The cheap, targeted assertion that would have caught §2, as a regression test
(no new module needed):

```python
# tests/test_holdout_guard_agreement.py
def test_seal_registry_and_collector_holdout_labels_agree():
    """The two holdout guards must see the same phrase set.

    seal_check seals phrases via is_holdout() over data/simulated/; the
    collector labels rows tierb_split='holdout'. Neither can see the other,
    so a row can carry a holdout label for a phrase that is not sealed (or
    vice versa) with nothing failing. Either direction is a defect:
      - labelled-but-unsealed  -> a stale/orphan label inflating the count;
      - sealed-but-unlabelled  -> a phrase analysed that should be withheld.
    """
    registry = sealed_registry("data/simulated", "ops/dashboard.json")
    rows = json.loads(Path("urgency_shift.json").read_text())["rows"]
    labelled = {r["clinical_prompt"] for r in rows
                if r.get("tierb_split") == "holdout"}
    assert not (labelled - set(registry)), "holdout-labelled but not sealed"
    assert not (set(registry) - labelled), "sealed but not holdout-labelled"
```

Not committed as a test this pass: it would fail immediately on the known
orphan row, and turning the suite red is the orchestrator's/owner's call, not
the critic's. Recommend fixing the orphan row first (drop rows whose
`clinical_prompt` matches no archive and whose `batch_index` is null), then
landing the test so the invariant is held going forward.

Second, cheaper suggestion: give the orphan-row warning a **threshold** so it
fails when it exceeds a set fraction of rows, rather than growing silently.
