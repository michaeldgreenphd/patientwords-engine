## HIGH · C1 — Two payloads published side by side on the same page disagree about n for the same two models

`data/convergence.json` and `data/model_stats.json` both feed **technical/ Part 4**, and
both were in this cycle's site push. `model_stats.json` was refreshed today.
`convergence.json` was **not** — it is still the 2026-08-20T12:40:27Z build — and the two
now state different sample sizes for the same models on the same page:

| model | convergence.json final point | model_stats.json (today) |
|---|---|---|
| apertus-8b-meditronfo | n_phrases **929**, mean -0.0239, CI [-0.0332, -0.0144], 39 down / 11 up | n_phrases **1215**, mean -0.0248, CI [-0.0336, -0.0162], 46 down / 17 up |
| meditron3-8b | n_phrases **931**, mean -0.0340, CI [-0.0427, -0.0251], 50 down / 13 up | n_phrases **1193**, mean -0.0329, CI [-0.0405, -0.0253], 57 down / 14 up |

Verified by re-running `scripts/convergence_tracker.py --site '' --out <scratch>` and
diffing against the committed site copy: the only changed keys are `models` and
`_provenance`, and inside `models` the only movement is the final accumulation point of
those two models. Point counts are identical (33 → 33), so this is pure staleness in the
tail, not a structural change.

**Root cause is the same shape as the open TIMELINE-CHAIN-GAP-20260820, but the open
decision names only `timeline.json`.** It is wider than recorded:
`scripts/convergence_tracker.py` is likewise absent from `docs/routine_standing_prompt.md`
§5 and from the `publish-site-data` skill, so no cycle runs it, while the site's own
`CLAUDE.md` describes `data/convergence.json` as "regenerated by the engine's nightly
cycle". `timeline.json` is also still stale (2026-08-20T12:46:17Z), i.e. the 08-20 cycle
ran both ad hoc and the 08-21 cycle ran neither.

Why the automated layer missed it: `validate_frontend_contract.py:304` shape-checks
`convergence.json` (`{"generated_utc": str, "scope": str, "models": dict}`) and nothing
more. `claim_check.py` guards prose *values* against their sources and passed clean —
correctly, because no page sentence hardcodes either n. Nothing anywhere asserts that two
published payloads agree with each other. This is the **same class** as the open
CLAIM-MANIFEST-PROPERTY-GAP-20260821: the manifest guards values, not properties, and
cross-payload consistency is a property.

Severity is HIGH because the inconsistency is *published and visible*: a reader comparing
the accumulation fold to the cross-model table on the same page sees 929 in one and 1,215
in the other for apertus. No confirmatory number is affected — both models are
post-registration exploratory, and their CIs exclude zero in both builds — so this is a
presentation-integrity defect, not a result defect.

**Feed forward — the check that would have caught it.** Not wired by this pass on purpose:
wiring it today would make the gate fail immediately on data this session is not
sanctioned to republish, which would block tomorrow's publish. Proposed, for the owner or
the orchestrating session to land in `validate_frontend_contract.py` beside the existing
per-file shape checks:

```python
# cross-payload: the accumulation fold's final point must agree with the published
# per-model statistics on n. Both feed technical/ Part 4; a stale convergence.json
# silently contradicts model_stats.json on the same page (critic 2026-08-22, C1).
conv = load("convergence.json")
stats = load("model_stats.json")
for model, block in (conv.get("models") or {}).items():
    pts = block.get("points") or []
    pm = (stats.get("per_model") or {}).get(model)
    if not pts or not pm:
        continue
    fold_n, stats_n = pts[-1].get("n_phrases"), pm.get("n_unique_phrases")
    if fold_n != stats_n:
        error("convergence.json", f"$.models.{model}.points[-1].n_phrases",
              f"accumulation fold says n={fold_n}, model_stats.json says "
              f"n={stats_n} - one of the two payloads is stale")
```

The durable fix is the publish chain, not the gate: add `convergence_tracker.py` and
`study_timeline.py` to §5 so the gate never has cause to fire. That is an owner call and
is why the existing decision entry is being widened rather than acted on.
