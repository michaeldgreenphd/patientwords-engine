## MEDIUM — two exporters disagree on JSON indent, so chain order silently swings the published payload by 4 MB

Found while diffing this cycle's republish. Three writers touch
`../patientwords/data/simulated_scenarios.json`:

| writer | line | indent |
|---|---|---|
| `scripts/export_frontend_simulated.py` | 406 | `indent=2` |
| `scripts/embed_scenario_joins.py` | 244 | `indent=2` |
| `scripts/export_traces_site.py` | 101 | **`indent=1`** |

Whichever runs **last** sets the format for the published file. The committed file
was `indent=1` (12,040,228 bytes), so the previous cycle happened to end on
`export_traces_site.py`. Running the chain in the order the standing prompt §5 lists
it — traces restamp early, `embed_scenario_joins.py` later — ends on `indent=2` and
produces **16,179,124 bytes: +34% on a payload every page fetches**, with an
identical line count (740,872) and no semantic change whatsoever.

This cycle caught it only because the diff read as 1,481,728 changed lines — every
line in the file. Re-running `export_traces_site.py --stamp-only` last restored
`indent=1` and reduced the real diff to 5,032 substantive lines. Had it gone
unnoticed, the cycle would have pushed a 4 MB regression to a public Pages site and
made every future payload diff unreadable — which would in turn have hidden the next
real data movement.

**Nothing encodes this.** `validate_frontend_contract.py` checks structure, not
serialization; `claim_check.py` checks numbers. Neither would have failed.

**Feed forward (proposed, not written — this is a code change, outside the cycle's
data mandate):**
1. Give the three writers one shared dump helper with a single `indent` constant, so
   chain order cannot change the format. Cheapest and correct.
2. Failing that, add a contract assertion: the payload's serialization must round-trip
   to itself under the canonical `indent`, and flag a size delta >10% with no scenario
   count change as an error, not a warning.

## RECURRENCE (not a new finding) — `--stamps` prefix-normalization comment is false

Already open as `STAMPS-NORMALISATION-20260821` (raised by the 2026-08-21 critic pass,
Finding 5; deck card D8). Recording that it **hit live again today**, on this cycle's
first exporter invocation — the second consecutive cycle to lose a round trip to it.
That is the argument for the one-line fix rather than continued documentation of the
workaround. Detail retained below for the owner reading this report standalone.

`scripts/export_frontend_simulated.py:110-116`. The comment at lines 111-115 states
that `--stamps` accepts "either spelling (bare stamp or `pairs_<stamp>` stem) and
normalise[s] to the bare stamp", and explicitly justifies this as a guard against a
past mis-publish. **Line 110 does no such normalization** — only `STEERED` (line 116)
strips the prefix.

The payload's own `batch` field carries the `pairs_`-prefixed stem, so a session that
derives its stamp list from the committed payload (the documented way to avoid
"silently dropping" a published stamp) and trusts the comment gets:

```
FileNotFoundError: data/simulated/pairs_pairs_20260706T201750Z.json
```

which is exactly what happened on this cycle's first exporter invocation. Harmless
here (it fails loudly and touches nothing), but it is a documented-but-false claim of
the kind the correction register exists for, and it costs every fresh session a
round trip.

**Feed forward:** either apply the same `.replace("pairs_", "", 1)` to line 110 that
line 116 already uses — making the comment true — or delete the comment. One-line
change either way; a regression test asserting `--stamps pairs_<stamp>` and
`--stamps <stamp>` resolve identically would pin it.

## LOW — the depth exporter's `--annotate` pin is recorded nowhere and is silently churnable

`scripts/export_jlens_depth.py` takes `--block`, `--exemplar-stem`,
`--exemplar-index` and `--annotate`. The first three are recoverable from the
committed `data/jlens_depth.json` (block ids, `exemplar.stem`, `exemplar.index`).
**`--annotate` is not.** Its effect is a per-block `annotation` object, and in the
committed file that field is `null` — indistinguishable from "the pin was passed and
produced nothing".

This cycle inferred an `--annotate urgency_downgrades_20260707T1:5` pin from the
payload's `examples` block (which does name that set and index, for an unrelated
reason) and passed it. The result populated `annotation` with
`"take my medication" becomes "take my health"` — i.e. **it changed the published
figure**. Caught by diffing against the committed file and re-run without the flag,
after which the file reproduced byte-identically except `generated_utc`.

The standing prompt and the publish skill both say pins change only on explicit owner
instruction. That rule is currently enforced by the operator noticing a diff, for a
pin whose correct value is unrecoverable from the artifact.

**Feed forward:** have `export_jlens_depth.py` record its full invocation (all pins,
including `--annotate`) into a `_pins` block in its own output, so the next cycle
reads the pins instead of inferring them. That single change makes the whole
pin-stability rule mechanically checkable.
