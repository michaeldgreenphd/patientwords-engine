# Work a pull request's review threads

Codex and Copilot both review every pull request in `patientwords` and
`patientwords-engine`. Their findings are **hypotheses, not defects**. The first
reviewed pull request (`patientwords#4`, 2026-09-04) produced three findings on a
two-file documentation change: two were real, one was a misreading. Plan for that
rate. Both failure modes cost — applying a wrong finding puts a defect into the
file the reviewers grade against; dismissing a right one ships the defect the
review existed to catch.

The rules themselves live in `AGENTS.md` (**Code Review Rules** and **Responding
to code review**), in one place, deliberately. This skill is the procedure, not a
second copy of the rules — do not restate them here.

## 1 · Read the whole PR, not just the wake

A wake names one event; the pull request may have more open. Get all of it:

- `pull_request_read` method `get_review_comments` — every thread, with its
  `is_resolved` and its GraphQL thread id (`PRRT_…`), which `resolve_review_thread`
  needs. The numeric id from the `#discussion_r…` anchor is what a *reply* takes.
  They are different ids; mixing them is the usual error.
- `pull_request_read` method `get` — `mergeable_state` and the head sha.
- `pull_request_read` method `get_check_runs` — CI on the current head.

A review body (`pull_request_review.submitted`) can carry a **suppressed** or
summary-only comment that never becomes its own thread. Read the review body too;
those still deserve a disposition, given in a reply on a related thread.

## 2 · Verify each finding against the file

Open the lines it names, on the current head. Ask what would have to be true for
the finding to hold, then check that, not the claim's plausibility.

- A finding about file contents or encoding: check the bytes (`od -c`), not the
  rendering. A trailing newline looks like a blank line in a diff view.
- A finding about a contradiction: read **both** places. The 2026-09-04 Codex P1
  was real precisely because the contradicted text was twelve lines up in the same
  file.
- A finding about a cross-file consequence: grep the repo. If the pull request
  itself created the staleness, fixing it belongs in this pull request rather than
  a follow-up — that is not widening scope.

## 3 · Fix, or decline with evidence

Small and local and verified → fix it. Then run the repo's own checks before
pushing: `python -m pytest -q` and `ruff check .` in the engine; in the frontend,
serve the pages and drive them (`AGENTS.md`, **Verifying changes**) when page JS
or data shape is touched.

Wrong, or right-but-larger-than-this-pull-request → do not push it. Say so.

## 4 · Reply on every thread, resolve only what you fixed

- `add_reply_to_pull_request_comment` with the **numeric** comment id: name the
  disposition and the commit, or the reason and the evidence.
- `resolve_review_thread` with the **`PRRT_…`** thread id, for fixed threads only.
  Resolving a thread you dismissed makes the pull request look handled when it is
  not.
- Every reply ends with the attribution footer (a blank line, `---`, then
  `_Generated by [Claude Code](https://claude.ai/code)_`).

## 5 · Ask for the re-review — a push does not trigger one

**Codex reviews on pull-request open, draft-ready, and an `@codex review` comment.
Nothing else.** A push, however large, does not re-trigger it. Copilot likewise
needs `request_copilot_review`. So after pushing review fixes, the new commits
are unreviewed until someone asks, and a pull request can sit looking reviewed
while its largest commit has never been read. (Observed on `patientwords#4`,
2026-09-04: the reviewed commit was the original two-file version; the fixes and
~120 lines of new rules after it had no automatic trigger.)

After any push that answers a review:

- comment `@codex review` on the pull request, naming which commits are new and
  what in them is worth checking — a specific pointer gets a better read than a
  bare re-request;
- call `request_copilot_review` for the other one;
- prefer claims a reviewer can check against the tree. Assertions about the
  repository ("this repo has no Python", "this file is the complete set") are
  where a fresh read pays; on 2026-09-04 pointing at three such claims returned
  two real findings.

## 6 · Stay on it until the pull request is done

Done is: CI green on the current head, `mergeable_state: clean`, every thread
either resolved or answered. Webhooks do not reliably deliver CI success or merge
conflicts, so re-check rather than assuming. Keep a check-in scheduled
(`send_later`) until the pull request merges or closes.

**Never merge or approve.** That is the owner's, on both repos.

## Never

- Never apply a finding you have not checked against the file.
- Never resolve a thread you did not fix.
- Never restate the review rules here or in `CLAUDE.md` — `AGENTS.md` is the one
  source, and a second copy is the drift that file exists to prevent.
- Never let a review push widen the pull request beyond the finding and what the
  finding made stale.
